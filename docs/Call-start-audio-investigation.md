# 接通初期音訊斷續排查

2026-11-04：使用者回報接通初期約一秒斷續，通話聽感與錄音均受影響；退出程式後尚未重現。這是排查線索，尚未經對照通話確認。

## 現有證據與修正

最近兩通本機日誌顯示：接通事件後查詢 `/record.htm`，約 1.2 秒後送出 `/Start`；沒有重複 Start 或舊狀態重設。RTP 開始後的統計未見丟包，最大收包間隔約 32ms。這些統計不能證明話機通話路徑的聲音正常，也不涵蓋 RTP 開始前的聲音。

事件伺服器原本送完 HTTP 回應後立即呼叫 `afterSend`，等回呼返回才關閉連線；命令工作緒可能在話機仍等待事件連線結束時，就反向請求話機。

本次改為：送完回應 → 移交回呼 → 連線擁有者關閉 socket → 執行回呼。傳送失敗時不執行回呼。保留原本的錄音命令、查詢、去重與 HTTP 請求間隔，不額外增加等待時間。此修正消除本機可重現的關閉順序問題，尚不能證明它是實機一秒斷續的根因。

## 驗證與實機待驗項目

`tests/event_close_native.cpp` 使用真實事件伺服器與 loopback socket，在回呼執行期間等待客戶端確認完整回應及 EOF。修正前失敗，修正後通過；測試不連線實際話機。

另以隔離的 x86 MSVC C++17 本機 build 執行 `tests/product_smoke.py`，11/11 通過，涵蓋事件、HTTP、控制協定與合成 RTP/WAV 流程。`git diff --check` 與修改檔案的 UTF-8 無 BOM／replacement character 掃描亦通過。結果保存在被 Git 忽略的 `docs/probe/call_start_20261104/`。測試執行檔位於該目錄，未替換日常使用的程式。

原生回歸測試在 x86 MSVC 開發者命令環境中，以產品相同的 C++17、`/MT /EHsc /utf-8 /DUNICODE /D_UNICODE /D_WIN32_WINNT=0x0601 /D_WIN32_IE=0x0800` 編譯 `tests/event_close_native.cpp`，使用 console subsystem，連結產品 build 所用的 Windows 程式庫；執行後應輸出 `PASSED response_close_before_callback`。完整產品回歸命令：

```powershell

```

實機仍須比較退出程式與修正版運行時的接通聽感，記錄斷續是否消失或仍與錄音開始同步；若仍發生，下一步區分話機啟動網路錄音的影響與通話網路問題。不能用延後錄音來宣稱已消除斷續。

撤回方式為還原本次事件伺服器關閉順序的修改；不涉及話機設定或既有錄音資料。

## 首次實機回測：仍有卡頓

替換測試版後，使用者回報仍有輕微卡頓。事件連線關閉順序修正尚不足以解決此症狀，不能標為實機修復完成。

以 session `s-f9b7-e85d` 的已完成錄音及日誌為證：接通事件於 16:54:07.087 收到，07.113 查詢錄音頁，08.285 送出 Start，09.077 收到話機控制資料，09.290 回覆控制握手並開始接收音訊。錄音為 8kHz／7 秒，350 個封包，丟包、重複、亂序與無效封包皆為零，最大收包間隔 32ms。PCM 檢查沒有整段零值；至少三個連續相同 20ms 區塊只出現在檔尾 6.92–7.00 秒。這些結果不構成聽感驗收，也不能排除話機送出音訊前的失真、停頓或通話路徑異常。

後續使用者澄清：這次通話聽筒正常，只有錄音回放有卡頓。排查重點因此改為檔案內音訊與播放器之間的區分，不應將本次回測直接解讀為通話音訊受干擾。

程式碼檢查發現內建播放器由 GUI 每 200ms 呼叫 `pump()` 補充音訊，四個 4096-byte 緩衝在 8kHz／16-bit mono 下合計約 1.024 秒。若 GUI 訊息處理停滯超過緩衝可支撐時間，存在播放斷流的可能；目前沒有證據證明這通回放實際發生該問題。下一步先以其他播放器播放同一 WAV，比較是否在相同位置卡頓。尚未據此改動播放器、增加錄音延遲、改動話機或再次替換程式。

## 外部播放器回測與 RTP 時間診斷

使用者確認其他播放器也會卡，因此本次症狀不僅限於內建播放器。先追查來源音訊與錄音處理；尚無理由將 GUI 補充播放緩衝視為這份錄音的根因。

原實作只解析 RTP 序號，忽略 timestamp 與 SSRC。[RFC 3550 §5.1](https://www.rfc-editor.org/rfc/rfc3550#section-5.1) 區分封包序號及音訊採樣時間；靜音期間未發送音訊也可能推進時間戳，所以時間跳躍本身不等同話機故障或網路丟包。既有 WAV／quality sidecar 沒有保存這些標頭，不能重建先前的時間線。

新增診斷保留 RTP timestamp／SSRC，對同一來源且序號連續的已接受封包計算 timestamp discontinuity、缺口採樣數及重疊／重設次數。另統計通過來源檢查的封包所呈現之 SSRC 變化，包括被既有序號篩選拒絕者。處理時間戳與序號的正常回繞，依前一封包的實際 payload 長度比較，不將已記為丟包的序號缺口再次算成來源時間缺口。

新增四個 quality sidecar 數值欄位：`timestamp_discontinuities`、`timestamp_gap_samples`、`timestamp_overlap_or_reset`、`ssrc_changes`。技術日誌保留前 100 個已接受封包中第一個及每五個封包的時間證據，每通最多八筆詳細時鐘不連續事件，以及結束摘要。無音訊 payload、來電姓名或號碼；既有序號篩選、PCM 解碼與 WAV 寫入行為維持原狀。這是有界的診斷補強，不是音訊修復或缺音補造。

x86 C++17 隔離 build 成功，`tests/product_smoke.py` 12/12 通過。新增整合案例涵蓋零丟包時的 800-sample 時間缺口、重疊、序號／時間戳回繞、payload 長度變化及來源切換；並逐 byte 確認 WAV PCM 與原解碼資料一致。輸出位於 `docs/probe/rtp_timing_20261104/`。需要以這個版本再錄一通，才能檢查實際來源的時鐘證據；尚未完成實機驗收。

## 開頭缺音：接通後重複查詢造成的延遲

使用者進一步回報「前一秒多的還是沒有」。以最新 session `s-b7fe-3af3` 為例：17:04:11.085 接通事件、11.154 完成錄音狀態查詢、12.448 Start 回應完成、13.256 收到控制資料、13.461 回覆握手，13.464 收到首包。接通至首包約 2.38 秒；其中接通後查詢與 Start 之間包含約 1.1 秒的 HTTP 靜默間隔。首批約 50 個封包在約 31ms 內到達，表示到達時間不能直接當成它們的採樣時間；不能據此把全部 2.38 秒都算成來源缺音。時間診斷有一次開頭重疊／重設，沒有正向時間缺口、SSRC 切換或封包丟失；仍不足以確定聽感異常的原因。

本次針對程式自身的啟動延遲，重用最近 65 秒內由受保護錄音頁確認的 `recordStatus=4`。來源為既有登入驗證或健康檢查；期限內接通可直接 Start，省去接通後重複 GET 及由該 GET 新增的 1.1 秒等待。仍遵守上一次 HTTP 請求後的靜默間隔；期限過後、未知／非 idle 狀態維持原查詢及舊狀態重設流程。任何 Start／Stop 嘗試都使觀察失效，Stop 的 HTTP 回應不當成 idle 證據。登入或狀態查詢失敗亦不沿用觀察。

此觀察不是對話機狀態的鎖定；若有其他管理端在觀察後操作話機，直接 Start 仍可能被拒絕。原本先 GET 再等待 1.1 秒也不提供原子狀態保證。65 秒期限對應預設 60 秒健康檢查及少量排程餘量，健康檢查停用或間隔更長時，超時仍重新查詢。

不提前到響鈴階段觸發、不改話機設定、不修改 WAV；話機啟動及握手仍有延遲，不能保證完整保留接通第一刻的聲音，既有缺音無法從 WAV 補回。隔離 build 位於 `docs/probe/early_start_20261104/`，尚需實機比較改善程度。

隔離 build 成功；完整回歸最終 13/13 通過（`product_retry/results.json`）。首次測試遇到日誌旋轉期間暫時無法讀取及新測試在舊 session 尚未完成清理時過早送出第二次 Start；保留原失敗日誌，測試改為等待健康狀態確認 session 清理完成，再驗證下一通必須重新查詢。重跑涵蓋原有全部案例並通過，未修改產品的 session 清理行為。

使用產品 `--stop` 正常退出機制的操作曾遭自動核准審查以 `blocked by policy` 拒絕，該操作未執行。其後使用者手動退出，已保留舊版備份、核對測試 build 的 SHA256 並完成替換及啟動；本機健康檢查確認 control/event 監聽、話機登入與本機檢查正常。新執行檔 SHA256 為 `76450ea85590476dfd83d1f8311e8ebcfaf5f35911d9ee3fb533d2deb578c16b`，實機開頭缺音改善程度仍待回測。
